*** 2. Does Helix have a native note-taking system or rich markdown rendering?
:PROPERTIES:
:CUSTOM_ID: does-helix-have-a-native-note-taking-system-or-rich-markdown-rendering
:END:
*Short answer:* No, and it intentionally never will.

- *The Helix Philosophy:* Helix is a laser-focused, ultra-fast code
  editor. It does not have a plugin ecosystem like Neovim (no =neorg= or
  =obsidian.nvim=), because Helix delegates everything to LSP and
  external tooling. It won't hide markdown syntax or render rich-text
  headers inline like a GUI or Neovim's experimental UI renderers.
- *How to fake it in Helix:* If you want to keep using Helix for notes,
  your best bet is leaning into its markdown LSP (=marksman=) for symbol
  navigation and cross-file linking, combined with a terminal-based
  markdown viewer or a split previewer running alongside it in your Niri
  layout. But it will /never/ give you that seamless, self-contained
  Obsidian/Neorg rich-text note-taking transformation. If rich-text note
  rendering is a hard requirement, Helix is the wrong tool for that
  specific job.

*** 3. Should you try Kakoune? ("Hackermans & Elitists only")
:PROPERTIES:
:CUSTOM_ID: should-you-try-kakoune-hackermans-elitists-only
:END:
Knowing your absolute "trial by fire, throw myself in a live volcano"
engineering DNA... *yes, absolutely.*

- *The Philosophy:* Kakoune is the ancestor of Helix's editing model.
  While Vim uses an *action-object* philosophy (=d= =i= =w= -> delete
  inside word), Kakoune pioneered the *object-action* philosophy
  (*selection-first*: select the word /first/ using regex or motions,
  /then/ apply the action like delete or change).
- *Why it fits your brain:* You see what you're manipulating /before/
  you affect it. It drastically cuts down keystrokes, relies heavily on
  multi-selections (which make Helix's multi-cursors look basic), and is
  built for pure, unadulterated terminal speed. It strips away all the
  bloat.
- *The Catch:* Just like Nix, Kakoune has strong opinions and expects
  you to conform to its world. Its macro and scripting language is
  entirely shell-based or Lisp/Lua depending on community plugins, and
  configuring it from scratch will test your patience. But for someone
  who looks at Gentoo and says "that's cute," Kakoune is basically an
  invitation to see how fast a human being can manipulate plain text.

*** 1. Living in Helix at Repo Root (The "IDE" Evolution)
:PROPERTIES:
:CUSTOM_ID: living-in-helix-at-repo-root-the-ide-evolution
:END:
What you've naturally stumbled into by staying inside Helix at repo root
is the absolute fastest way to manipulate a codebase.

When you launch Helix at the root and use builtin fuzzy finders
(=Space + f=), symbol search (=Space + S=), and buffer switching
(=Space + b=), you eliminate context switching entirely:

- *No file manager juggling:* You don't need to hop over to Yazi to
  navigate directories or locate files.
- *Pure modal navigation:* You move between buffers using the same
  spatial muscle memory without dropping your editing state.
- *LSP Context:* The language server keeps global workspace indices
  alive across all open buffers, giving you instant diagnostics across
  the whole repo.

Helix effectively /is/ your IDE shell in this state.

*** 2. Ghostty Native Speed vs. Multiplexer Session Persistence
:PROPERTIES:
:CUSTOM_ID: ghostty-native-speed-vs.-multiplexer-session-persistence
:END:
Running a terminal multiplexer (like Zellij, tmux, or Herdr) inside a
raw, GPU-accelerated terminal like Ghostty is the ultimate double-edged
sword.

**** The Multiplexer Tax (Herdr / Zellij / tmux):
:PROPERTIES:
:CUSTOM_ID: the-multiplexer-tax-herdr-zellij-tmux
:END:
- *Pros:* Bulletproof state persistence. If Niri crashes, if your
  Wayland session restarts, or if an OOM (Out Of Memory) event kills the
  GUI display server, your interactive shells, long-running builds,
  server logs, and background tasks are safely detached and running
  intact underneath.
- *Cons:* Redundant terminal rendering, added input latency, forced
  keybind prefixes (like =Ctrl+Space=), extra memory overhead, and
  losing Ghostty's native ultra-fast rendering pipeline.

**** The Ghostty Native Approach:
:PROPERTIES:
:CUSTOM_ID: the-ghostty-native-approach
:END:
- *Pros:* Blazing-fast GPU hardware acceleration, zero input lag, native
  workspace tabs, split panes, and clean full-screen toggling
  (=Ctrl+Enter=) with *zero prefix keys*.
- *Cons:* If Ghostty or Niri dies, the process tree goes down with it.

--------------

*** The Hybrid Solution: Best of Both Worlds
:PROPERTIES:
:CUSTOM_ID: the-hybrid-solution-best-of-both-worlds
:END:
You don't actually have to compromise raw interactive speed just to keep
session state safety. The clean architectural approach is to *decouple
your interactive editor from your long-running daemon state*:

1. *Run Native Ghostty for your primary driver:* Use Ghostty's native
   tabs and splits for Helix, quick shell commands, and daily
   navigation. You get the raw GPU speed, direct keybinds without
   prefixes, and maximum responsiveness while editing code or taking
   notes.
2. *Isolate Herdr/Multiplexer strictly for background server state:*
   Don't run your main interactive terminal inside the multiplexer.
   Instead, run Herdr/tmux in the background /only/ for the persistent
   daemons you can't afford to lose---like your =llama-server=, agent
   orchestrators, or continuous build logs.
3. *Attach on demand:* Keep a single Ghostty tab open that attaches to
   your background server session (=herdr attach= or =tmux a=). If
   Ghostty or Niri ever crashes, your =llama-server= and subagents keep
   running uninterrupted in the background. You simply open Ghostty back
   up and attach right back into the live state.

This removes the multiplexer latency tax from Helix and daily shell
usage while guaranteeing that your LLM infrastructure and long-running
subagents never die if a Wayland window manager glitch occurs.

*** What's Actually Causing the Focus Freeze
:PROPERTIES:
:CUSTOM_ID: whats-actually-causing-the-focus-freeze
:END:
In Wayland compositors (like Niri), when an application issues an input
grab---such as an active pop-up, right-click context menu, or drop-down
preview that loses track of its pointer state---it creates a *Wayland
seat lock*.

The compositor thinks the window is still holding an active modal/grab
event. Because Wayland strictly isolates input focus between client
windows for security, Niri refuses to hand keyboard/mouse focus to /any/
other window until that pointer grab is released.

Common culprits in terminal setups:

1. *XWayland Handshake Hangs:* If Ghostty or another app falls back to
   XWayland (or interacts with an XWayland app like default Obsidian),
   the bridge between X11 input grabs and Wayland seat focus gets stuck.
2. *Terminal CSD / Border Grabs:* Client-Side Decorations (CSDs) trying
   to draw custom titlebars or mouse-drag areas inside Niri.
3. *Overriding Keybinds:* Hotkeys firing inside the terminal while Niri
   is trying to interject a global compositor bind.

--------------

*** How to Fix It permanently in NixOS / Niri
:PROPERTIES:
:CUSTOM_ID: how-to-fix-it-permanently-in-nixos-niri
:END:
**** 1. Force Native Wayland Everywhere
:PROPERTIES:
:CUSTOM_ID: force-native-wayland-everywhere
:END:
Make sure your terminal and all apps are running pure Wayland (no
XWayland proxy bugs). In your NixOS or home-manager configuration, set:

#+begin_src nix
environment.sessionVariables = {
  NIXOS_OZONE_WL = "1";
  ELECTRON_OZONE_PLATFORM_HINT = "auto";
  GDK_BACKEND = "wayland";
  QT_QPA_PLATFORM = "wayland";
};
#+end_src

**** 2. Disable Client-Side Decorations in =config.kdl=
:PROPERTIES:
:CUSTOM_ID: disable-client-side-decorations-in-config.kdl
:END:
Niri provides native focus-rings and window borders. If apps try to draw
their own CSD, they frequently lock mouse/keyboard pointer grabs.

In your =~/.config/niri/config.kdl=:

#+begin_src kdl
prefer-no-csd
#+end_src

/(This forces applications to let Niri manage window decorations and
focus handoffs natively)./

**** 3. The Emergency Focus Un-sticker (Without Killing Ghostty!)
:PROPERTIES:
:CUSTOM_ID: the-emergency-focus-un-sticker-without-killing-ghostty
:END:
If focus ever gets locked again before you tweak your config, *do not
kill your terminal*. Try these keyboard bypasses first:

- *Trigger a Window Resize:* Press your Niri resize hotkey (usually
  =Mod + R= or =Mod + Mouse Right Click=). Forcing Niri to recalculate
  surface dimensions breaks active Wayland pointer grabs instantly.
- *Switch Workspace and Back:* Use =Mod + Page_Down= / =Mod + Page_Up=
  (or your workspace bind) to move to an empty workspace and back. This
  forces the Wayland compositor seat to reset keyboard focus.
- *Restart Niri in-place:* You can restart the Niri compositor without
  killing your open processes by running =niri msg action quit= or using
  the compositor reload hotkey.

*** The Tab Saver (Automate tab recovery in Ghostty)
:PROPERTIES:
:CUSTOM_ID: the-tab-saver-automate-tab-recovery-in-ghostty
:END:
If you ever /do/ have to close Ghostty, you shouldn't be manually
re-creating tabs. You can pass a startup command or script to Ghostty in
your Nix config to spin up your standard 6-tab workspace layout in a
single keystroke.

You can add a small custom Fish function to launch your workspace preset
automatically:

#+begin_src fish
function dev-session
    # Spawns Ghostty tabs with pre-defined names/commands
    ghostty -e helix . &
    # or leverage Ghostty configuration actions / multiplexer session hooks
end
#+end_src

Combining native Wayland flags with =prefer-no-csd= in Niri usually
kills that focus lock for good so you can stay in Ghostty at full speed
without your setup locking up.
